# Linux 生产环境实战：性能瓶颈排查（CPU/内存/IO）

当服务器出现卡顿、应用无响应或 SSH 登录缓慢时，通常是由 CPU 过载、内存耗尽或磁盘 IO 阻塞引起的。本章聚焦系统底层“三大件”的排查手段与故障处理。

> **返回总览**：[00-linux-ops-overview.md](00-linux-ops-overview.md)

---

## 1. CPU 与系统负载排查

**核心目的**：确认系统当前的整体压力，并揪出消耗 CPU 资源的具体进程或线程。

### 常用命令

```bash
# 查看系统负载（过去 1、5、15 分钟的平均活跃进程数）
uptime

# 动态查看系统状态与进程排名
top

# 查看特定进程下所有线程的资源占用
top -Hp <PID>
```

### 运行手段与排查逻辑

- **判断系统是否过载**：`load average` 的值不应超过服务器的 CPU 核心数（可通过 `nproc` 查看）。若负载远超核心数，说明有大量进程在排队。
- **在 `top` 中定位元凶**：
  - 按大写的 `P` 键：按 CPU 使用率从高到低排序；
  - 观察 `%CPU` 和 `%MEM` 列，记录高占用进程的 PID。
- **线程级排查**：若 Java 或 Python 等多线程程序吃满 CPU，用 `top -Hp <PID>` 找到具体的线程 TID，方便开发人员通过 `jstack` 或 `perf` 进一步定位代码死循环。

### 故障解决方案

- **程序死循环跑满 CPU**：定位到 PID 后，若非核心业务，可直接 `kill -9 <PID>` 终止；若是核心业务，需保留现场，通过 `strace -p <PID>` 或抓取线程栈交由开发排查。
- **大量短命进程消耗 CPU**：检查是否有定时任务（Crontab）执行过于频繁，或系统被植入挖矿脚本。

## 2. 内存瓶颈与 OOM Killer

**核心目的**：排查内存是否真正耗尽，并确认进程无故消失的原因。

### 常用命令

```bash
# 以人类可读方式查看内存
free -h

# 在 top 中按内存占用排序（进入 top 后，按大写的 M 键）
top

# 查看系统内核日志中的 OOM 记录
dmesg | grep -i oom
```

### 运行手段与排查逻辑

- **避免被 `used` 欺骗**：Linux 会将空闲内存用作缓存（buff/cache）。真实的可用内存看 `available` 列。只要 `available` 还有较多剩余，系统内存就是健康的。
- **排查进程消失**：若应用程序突然消失且日志无报错，必须查 `dmesg`。若看到 `Out of memory: Killed process <PID>`，说明内存耗尽触发了内核的自我保护机制（OOM Killer），内核强制杀死了占用最高的进程。

### 故障解决方案

- **防患于未然**：对核心服务（如 Java、MySQL）在 Systemd 或容器编排中设置硬性的内存限制（如 `MemoryMax`），防止单个程序内存泄漏拖死整台机器。
- **紧急释放内存**：若确认是缓存过大影响了应用，可执行 `sync && echo 3 > /proc/sys/vm/drop_caches` 手动释放缓存（生产中慎用，会导致短期内磁盘 IO 飙升）。

## 3. 磁盘 IO 阻塞排查

**核心目的**：排查系统负载极高但 CPU 空闲的异常情况（通常是因为磁盘读写慢导致进程阻塞）。

### 常用命令

```bash
# 监控磁盘 IO 压力（需安装 sysstat）
iostat -x 1

# 找出疯狂读写磁盘的进程（需安装 iotop）
iotop -o

# 查找处于不可中断睡眠状态（D 状态）的进程
ps -eo pid,ppid,stat,comm | grep " D "
```

### 运行手段与排查逻辑

- **读懂 `iostat`**：
  - `%util`：磁盘的繁忙度。如果持续接近 100%，说明磁盘性能已达瓶颈（机械硬盘极易跑满）；
  - `await`：平均 IO 等待时间。数值越大，说明应用写入越慢。
- **定位 IO 元凶**：运行 `iotop -o`，屏幕会动态显示哪个进程正在疯狂写入（DISK WRITE）或读取。
- **D 状态进程**：`load average` 很高，但 `top` 里 CPU 和内存都不高，且 `ps` 发现大量 D 状态（Uninterruptible Sleep）进程，代表它们卡在等待硬件响应（通常是磁盘或 NFS 网络存储）。

### 故障解决方案

- **死循环刷盘**：通过 `iotop` 发现日志服务或数据库大量写盘，检查是否因为开启了 Debug 日志，或遇到了慢查询。
- **磁盘寿命/故障**：若 `iostat` 显示磁盘读写极慢，且排除了软件并发问题，需检查 `dmesg` 是否有 `I/O error`，这通常是硬盘坏道或云盘限流的前兆，需准备数据备份与硬件更换。

## 4. 生产视角推演：性能基线建立
- **历史指标留存**：在故障发生时，`top` 只能看当下。生产环境应部署 `sysstat` 服务，通过 `sar -u 1 3` 查看历史 CPU 负载，或通过 `sar -r` 查看历史内存趋势，以便事后复盘。
- **压测前置**：任何新服务上线前，必须使用 `wrk` 或 `jmeter` 进行压力测试，确定其 TPS 和资源消耗基线，再根据基线配置 K8s 的 `resources.limits` 和 `requests`。
